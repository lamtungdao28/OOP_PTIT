# Manual Mock Data

`demo-data.sql` is a MySQL 8.4 seed script for the current entities.
This task only creates the files. The SQL has NOT been run against any database.

This folder is deliberately outside `src/main/resources` and is not wired to
Spring SQL initialization, Flyway, Docker initialization or application startup.
The older `src/main/resources/db/mock-data.sql` remains unchanged.

## Accounts

| Username | Role | Profile code |
| --- | --- | --- |
| demo.admin | ADMIN | DEMO-AD001 |
| demo.lecturer.01 | LECTURER | DEMO-GV001 |
| demo.lecturer.02 | LECTURER | DEMO-GV002 |
| demo.lecturer.03 | LECTURER | DEMO-GV003 |
| demo.student.01 through demo.student.20 | STUDENT | DEMO-SV001 through DEMO-SV020 |

There is no default password. By default all accounts are INACTIVE and their
password fields contain non-login markers. They cannot authenticate, and an
existing authorized account is needed to inspect the data through admin APIs.

For optional login testing, generate a BCrypt hash with the project's
`PasswordEncoder` for a password you choose. Set the SQL session variable
`@demo_password_hash` to that hash in the same connection before a future manual
import. Do not supply plaintext, commit a real password/hash, or use production
credentials. The script checks the BCrypt format before enabling accounts.
This optional hash is shared by the newly inserted fixture accounts, including
the demo admin, so this mode is for an isolated development database only.
`demo.student.20` stays INACTIVE even when a valid hash is provided.

Re-importing with a hash will NOT activate accounts inserted earlier: existing
users, password hashes and statuses are never updated by the script.

## Classes and Scenarios

| Class code | Lecturer | Students | State |
| --- | --- | --- | --- |
| DEMO-CLASS-01 | DEMO-GV001 | DEMO-SV001..010 | ACTIVE |
| DEMO-CLASS-02 | DEMO-GV001 | DEMO-SV006..015 | ACTIVE |
| DEMO-CLASS-03 | DEMO-GV002 | DEMO-SV011..020 | ACTIVE |
| DEMO-CLASS-04 | DEMO-GV002 | DEMO-SV001..008 | INACTIVE, historical |
| DEMO-CLASS-05 | DEMO-GV003 | DEMO-SV013..020 | ACTIVE; SV020 enrollment INACTIVE |
| DEMO-CLASS-06 | DEMO-GV003 | None | INACTIVE, no sessions/enrollments |

Each active class has four class sessions. For example, DEMO-CLASS-01 has:

| session_no | Scenario | Intended API checks |
| --- | --- | --- |
| 940011 | Tomorrow, not opened | GET attendance returns 404; POST open can create a session |
| 940012 | OPEN with 4 recorded students | Manual recording, duplicate 409, pagination/statistics, closing |
| 940013 | CLOSED with all 10 active enrollees recorded | Results, PATCH corrections, idempotent close |
| 940014 | Yesterday, stored OPEN but expired, 2 recorded students | Manual 409; close fills missing ABSENT |

Classes 02, 03 and 05 use the same pattern with session numbers `94002x`,
`94003x` and `94005x`. Historical class 04 has two fully recorded CLOSED sessions,
`940041` and `940042`. Enrollments may remain ACTIVE in an INACTIVE historical class.

Dates are relative to the SQL execution time, not the time the file was created.
Fresh OPEN deadlines are approximately 1.5 to 2.5 hours after import, rounded to
half past the target hour. Early opening is allowed by the current service,
including when the target class session begins after midnight.
Re-import does not refresh dates, reopen sessions or reset corrected attendance.
After expiry, GET reports effective CLOSED but `/close` is still needed to
persist missing ABSENT records.

In a fresh DEMO-CLASS-01 OPEN session, students 001..004 are already recorded,
005..010 are unmarked, and 011 is not enrolled. Student 001 is PRESENT and 002 is
LATE. Lecturer 02 or 03 cannot manage this class; ADMIN/STUDENT cannot use the
lecturer-only attendance APIs. These cases provide both successful and rejected
requests without requiring arbitrary IDs from a different dataset.

## IDs and Safety

- Primary keys are generated by MySQL; all foreign keys resolve from fixture codes.
- `session_no` is globally unique in the current entity. Numbers 940011..940054
  are reserved for this dataset and are NOT API path IDs.
- `/api/sessions/{id}/...` uses `class_sessions.id`. The legacy class-based
  recording API uses `attendance_sessions.id` in its body. PATCH uses `attendance.id`.
- Final SELECT statements list generated class, class-session, attendance-session
  and student IDs when the file is eventually imported manually.
- The exact legacy spellings `class_seesionsid` and `attendnce_sessionsid` are
  preserved. User roles remain ordinal: STUDENT=0, LECTURER=1, ADMIN=2.
- No schema is created or selected, and no existing rows are updated/deleted.
  Select the intended development schema yourself before any future import.
- Inserts skip existing natural keys/student-session records. This supports
  sequential re-imports of an intact dataset, not concurrent seed runs.
- Keep DEMO codes/usernames and reserved session numbers separate from real data.
  Conflicting existing unique values can cause skips or constraint errors.
- Use a fresh connection with application writers stopped. Execute the file in
  one transaction/session, stop on the first error and ROLLBACK. Do not use
  continue-on-error mode. Review the script before any eventual import.

Only source/static checks are appropriate for the current request. No database
connection, import command, startup hook, or SQL execution is performed here.
